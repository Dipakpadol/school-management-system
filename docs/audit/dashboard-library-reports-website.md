## Source traces and evidence

- Dashboard: `frontend/lib/src/features/dashboard/presentation/dashboard_page.dart` → dashboard controller/repository/remote data source → `modules/dashboard/api/DashboardController.java` → `DashboardService.summary()/todayAttendance()` → `StudentRepository`, `UserAccountRepository`, `StudentFeeAssignmentRepository.summarizeAll()`, `AttendanceRecordRepository.findTodayDashboardRecords()`, `StudentClassAssignmentRepository.countActiveStudents()`, `AuditLogRepository`. `List.of()` is returned for summary notifications and class-wise attendance. `safeValue()` catches every RuntimeException and converts to zero/empty; the frontend cannot distinguish outage from zero. `DashboardServiceTest` tests mocked aggregation/fallback, not role-scoped live DB behavior.
- Reports: `frontend/lib/src/features/reports/presentation/pages/reports_page.dart` → report repository/remote datasource → `ReportsController.export()` → `ReportsService.export()`. Student export calls parameterless `exportExcel()/exportCsv()`; fee exporters likewise take only format. EXAM_RESULT_REPORT maps to `ModuleRecordService.export*("EXAMS", "results", ...)`; HOSTEL_OCCUPANCY_REPORT maps to `ModuleRecordService.export*("HOSTEL", "allocations", ...)`. Those are not the typed exam_results and hostel allocation repositories. All seven request filter fields in the UI are therefore not proof of functioning filtering. No dedicated ReportsService test was present during baseline inspection.
- Communication: `notification_management_page.dart` → notifications repository/datasource → `NotificationsController` → `NotificationService` → `NotificationTemplateRepository`/`NotificationLogRepository` → notification templates/logs tables. `DefaultNotificationProvider` supports SMTP/configured HTTP; `NotificationService.sendNotification(PUSH, ...)` explicitly fails. `FeeDueReminderScheduler`, `PublicEnquiryService`, and matching tests are real integration points. Provider tests and service mocks are not evidence of live provider delivery.
- Portals/library: `app_router.dart`, `app_routes.dart`, `module_registry.dart`, `menu_policy.dart`, user seeders, all backend module paths, and all migrations were searched. Existing menu labels such as `API ready` have no completeness authority. No library CRUD route/service/table or ownership-scoped portal endpoints were found.

## Public website and shared frontend baseline

Eight public pages exist: home, about, admissions, academics, facilities, gallery, events, contact. Admission/contact forms call the central public enquiry service and have backend/frontend tests. Public image rendering is remote Unsplash (`public_website_data.dart`, `PublicNetworkImage`, `_HomeHero`); the Flutter asset manifest currently registers no local images. About/facilities cards use icons without the requested photography. School phone is `+91 XXXXXXXXXX`; admissions say Class X while programs/events claim Class XII. Events are static and have past hardcoded dates. No verified quick statistics or testimonials were found and they must not be invented.

Common widgets already include AppButton, AppTextField, AppSelectField, AppLoadingState, AppErrorState, AppInfoCard and AppDataTable. Preserve these. Many pages define their own inline form/error/dropdown widgets, so consistent header/filter/status/confirmation/pagination abstractions remain incomplete. Reports dropdown dependent values reset in state but use `initialValue` without stable identity keys, risking stale form display after master changes. Report dates lack ordered-range validation. Most data tables and reports still need meaningful role/empty/error and filter regression coverage. Only two frontend test files exist at baseline, both public enquiry related.

Performance opportunities verified in this subset: dashboard pulls every daily attendance entity and related students/hierarchy to count statuses in memory; report/export helpers read full datasets; multiple summary queries have no explicit transaction boundary; notifications make synchronous network calls in database transactions. Root and module owners should profile other domain screens before claiming performance work complete.

## End-to-end evidence

### Fees & Accounts

The navigation routes in `frontend/lib/src/app/router/app_router.dart:201` and `:301` lead to `fees_management_page.dart`, `student_fee_assignment_page.dart`, `fee_assignments_page.dart`, `fee_defaulters_page.dart` and `payment_collection_page.dart`. Their providers in `features/fees/presentation/controllers/fees_providers.dart` call `FeesRepositoryImpl`, then `FeesRemoteDataSource`. API constants at `core/constants/api_paths.dart:150` match `FeeController`'s `/v1/fees` mappings. The backend calls `FeeService`, `FeeImportExportService`, `FeeMapper`, typed repositories and the fee entities. Financial mutations are transactional and entities inherit `BaseEntity.@Version` and audit fields.

Class assignment is implemented, including the previously reported empty-class scenario: `StudentFeeAssignmentPage._submit` posts `feeStructureIds`, academic year, class ID and `skipExisting`; `FeeService.assignFeeToClass:461` validates scope/hierarchy, persists `ClassFeeAssignment` before iterating students, and returns warnings if no students exist. V25 defines class fee mappings **without a legacy mapping backfill**. `assignActiveClassFeesToStudent:317` uses these persistent mappings and skips student/structure duplicates. Therefore this should be regression tested, not replaced based on an old symptom alone; legacy active class structures must be examined before assuming newly admitted students receive them.

`FeeService.searchAssignments:765` uses `FeeAssignmentSpecifications` and a paginated repository. `findDefaulters:992` uses the real installment due dates and unpaid/cancelled exclusions. The Flutter paths `/v1/fees/assignments` and `/v1/fees/defaulters` exist and the data envelope matches `PagePayload`. These endpoints are not absent. Their data completeness and filters are defective as described below.

`StudentService.createStudent:86` invokes class auto assignment, creates requested hostel/transport allocations, then assigns matching central fees. `assignClassSection:244` and `updateClassAssignment:261` evaluate new class fees. `updateStudentProfile:144` only updates profile fields and does not re-evaluate applicable fees. Import invokes student creation and separate hostel/transport service assignment paths; failures can be reported as row warnings after a student has been created. Central auto assignment queries verify an active allocation, match applicable structures, skip duplicates and audit (`StudentFeeAutoAssignmentService`). New fee structures added after an existing allocation do not automatically backfill all existing occupants unless manual assignment occurs.

Payments have central `FeePayment`, `FeePaymentAllocation`, `FeeReceipt` records and per-installment balances. Refund, reverse and void exist as full-payment status transitions; they reverse allocations and cancel the receipt. They are bookkeeping operations; `ONLINE` is a payment-mode label, not a payment gateway integration. Refund requests have no partial amount or gateway refund reference. Existing tests cover category/structure restrictions, multi-structure and empty-class assignment, auto class mappings, discounts, collection/reference/overpayment and late fees. They are mocked service tests; no database/controller/browser fee lifecycle is certified by them.

### Hostel

`HostelManagementPage` uses `hostel_providers.dart` → `HostelRepositoryImpl` → `HostelRemoteDataSource` → `/v1/hostels` constants → `HostelManagementController` → `HostelService`/`HostelMapper` → typed hostel repositories → V17 tables (`hostels`, `hostel_rooms`, `hostel_beds`, `hostel_allocations`, `hostel_fee_structures`). Room form changes generate/deactivate numbered beds via `HostelService.syncBeds:588`. Room details read actual allocations and calculate occupied/available beds. Student profile routes in the student controller call the same service.

The hostel fee list contract is present: `HostelService.listFeeStructures:498` returns PageResponse and `HostelRemoteDataSource._unwrapList` accepts both `data.content` and a list. It does silently lose pagination. The legacy `HostelController` still exposes generic module records at `/v1/hostel`; that is not evidence for building/warden/mess/attendance integration into typed allocations.

### Transport

`TransportManagementPage` uses `transport_providers.dart` → repository → `TransportRemoteDataSource` → `/v1/transport` constants → `TransportController` → `TransportService`/`TransportMapper` → repositories → V20 tables (`transport_drivers`, `transport_vehicles`, `transport_routes`, `transport_pickup_points`, `student_transport_assignments`, `transport_fee_structures`). Vehicle links driver, route links vehicle, stop links route, and a student assignment stores year/vehicle/route/stop. Requests validate academic year and route/stop membership. Fee structures have a central backing `FeeStructure` and fee assignments carry route/stop source identifiers.

No hostel or transport service tests were found in `src/test` at baseline. Existing frontend tests do not exercise their full workflows.

## Prioritized confirmed defects and risks

1. **Discount does not reliably reduce debt.** `StudentFeeInstallment.discountableBalance` returns amount minus prior discounts, ignoring payments. `StudentFeeAssignment.applyDiscount` allocates against the earliest installment even if paid. Reproduction from code: two installments of 100, collect 100 (first installment paid), apply global discount 50: the first installment becomes payable 50 with paid 100; its balance is clamped to zero, while the second remains 100. The recorded discount is 50 but total pending remains 100. Add a regression test and limit discounts to unpaid eligible balances; reject unallocatable discounts instead of silently recording them.
2. **Cancelled financial records can still mutate.** `FeeService.collectPayment:814`, `applyDiscount:776` and `assessLateFees:804` do not reject cancelled assignment status. `StudentFeeInstallment.cancel` changes only status, leaving outstanding balances. `deleteAssignment:914` soft-deletes any assignment, including payment history. Introduce explicit lifecycle guards and preserve financial records.
3. **Allocation transfer flush ordering.** `HostelService.changeRoom:385` and `TransportService.changeStudentAssignment:545` change the prior status then persist replacement without flushing the old status. V17/V20 partial unique indexes permit only one active student/year allocation. Hibernate commonly flushes entity inserts before updates; a real PostgreSQL regression must prove and fix this risk with explicit transition flushing.
4. **Capacity race.** `HostelService.validateRoomAvailable:648` and `TransportService.validateVehicleAvailable:815` count active assignments then insert without locking a shared room/vehicle row. Independent student inserts do not change the version of the room/vehicle. The same race affects capacity reduction against concurrent allocations. Add shared pessimistic locking and a real database concurrency test.
5. **Same-capacity transfer false rejection.** Availability is checked before releasing the existing allocation, so changing a stop on one's already-full vehicle or a bed within a full room fails. Exclude/release the old occupancy inside the locked transaction before validating replacement.
6. **Inactive transport targets on transfer.** `createActiveAssignment:591` calls `validateTransportActive`; `changeStudentAssignment:545` only resolves hierarchy and checks capacity. Transfer can allocate to an inactive vehicle, route or pickup point.
7. **Future charges remain after service ends.** `TransportService.removeStudentAssignment:575` and hostel `vacate:419` only change allocation status. Transfer only adds new fees. Existing unpaid future installments remain due, including charges from a former route/room. Preserve accrued/paid history and reconcile future unpaid installments by effective date and source. Existing fee assignment source reference points to the scope, not an individual allocation, so readmission requires deliberate handling.
8. **Section filters are inconsistent.** `FeeService.findDefaulters:996` converts section ID to name then repository compares `assignment.sectionName`, which is copied from the fee structure. Class-wide structures commonly have no section, so a real child's class-wide dues disappear under a section filter. `FeeAssignmentSpecifications` instead joins all class assignment history and does not restrict active/academic-year matching, allowing historical section leakage. Use the student's matching academic-year enrollment consistently.
9. **Lists/exports truncate valid data.** `PageRequestDto` defaults to 20. Category/structure and hostel/transport fee remote calls omit page/size and unwrap only content. Fee assignment/defaulter calls hardcode size100; repositories/providers discard totals/page and screens have no server-page navigation. `FeeImportExportService.defaulterReport` requests only page0,size200. More than 200 defaulters are omitted from exports.
10. **Heavy list payloads and queries.** `FeeService.searchAssignments` maps every row with the full assignment mapper (student enrollment, structure categories, installments, discounts, payments, receipt, allocations). The specification does not eagerly fetch these relationships. Defaulter repository applies collection entity graphs to pageable results, risking in-memory pagination and row multiplication. Class student listing queries each student's assignments. Split list/detail DTOs or batch fetching, preserving existing API compatibility.
11. **Reports are aggregate snapshots, not complete accounts reports.** `FeeImportExportService.collectionReport` hardcodes empty filters and exports one summary row; report totals include cancelled assignments. There is no date-range/category/mode-filtered collection ledger or online settlement/refund integration. Fees frontend imports discard ImportResultDto and may show success despite validation errors.
12. **Permission granularity and audit attribution.** Backend FEES_MANAGE governs create/update/delete/collect/refund; FEES_READ permits export. `approvedBy`, `collectedBy` and `processedBy` are request fields and can misrepresent actors, although separate audit fields record authenticated actors. Preserve audit identity and add action permission checks coordinated with central RBAC.
13. **Optional fee flags disable automatic fees.** `HostelAssignmentRequest.appliesHostelFee` and `TransportAssignmentRequest.appliesTransportFee` return false for null. Import parsers preserve null when the fee-applicable column is blank. A valid allocation with omitted optional flag therefore silently skips fees, contrary to automatic applicable-fee evaluation; explicit false can remain an intentional exemption while null defaults to evaluation.
14. **Legacy class assignment migration gap.** V25 creates the mapping table without inserting mappings for existing active class structures/assignments. The new auto assignment service queries only this table. Existing installations can therefore stop automatically assigning class fees until a user manually reassigns each class. Backfill only mappings supported by the existing hierarchy and evidence, preserving duplicates and financial history safely.

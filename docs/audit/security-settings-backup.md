## Trace evidence

- Users: `frontend/lib/src/features/users/presentation/pages/users_page.dart` → `users_remote_data_source.dart` → `modules/users/api/UserController.java` → `UserService.java` / `UserImportExportService.java` → `UserAccountRepository.java` / `UserAccountSpecifications.java` → `UserAccount.java`, `Role.java`, `Permission.java` → V2, V15, V23, V24. Search specifications do not exclude signup-source users. User create/update role payload is enum-bound while roles can have arbitrary names.
- Roles: `frontend/lib/src/features/settings/presentation/pages/role_permission_page.dart` → `settings_remote_data_source.dart` → `RoleController.java` → `RoleService.java` → role/permission repositories → same central auth tables. Older `/users/roles/{id}/permissions` uses a second mutation implementation in UserService with different validation. Settings UI itself has no duplicate role tab.
- Authentication: `auth_controller.dart` / auth repository → `AuthController` → `AuthService` → user/refresh/reset repositories. `SecurityConfig.jwtAuthenticationConverter()` reads only signed role/permission claims through `SchoolJwtGrantedAuthoritiesConverter`; it never reloads active user/role/permission state. `JwtService` and `SchoolUserPrincipal` iterate all attached roles/permissions without status filtering.
- Login: `AuthService.login()` catches authentication failure, calls `recordFailedLogin`, then throws a runtime BusinessException inside default `@Transactional`; counter and lock updates roll back. No failed-attempt audit is emitted. `UserAccount.isLocked()` treats any LOCKED status as permanent even after lockedUntil passes.
- Settings: `SettingsPage` → settings providers/repository/datasource → `SettingsController` → `ApplicationSettingsService` → `ApplicationSettingRepository` → `ApplicationSetting` / V24. Defaults and allowed keys establish only five real configuration groups. Academic-year value is not verified against academic_years.
- Audit: `audit_logs_page.dart` → audit API service → `AuditLogController` → `AuditLogService`/export service → `AuditLogRepository`/specifications → `AuditLog` and V1/V5. `record` uses MANDATORY and standalone methods use REQUIRES_NEW. Important mutation audits have before/after DTOs, while login only has successful actions.
- Backup: repository-wide search for backup/restore reveals no domain workflow/controller/screen; BaseEntity.restore() is soft-delete restoration, not database restoration.

## Verification limits at baseline

Existing tests include AuthService/JwtService mocks, protected endpoint annotation checks, selected MockMvc authorization, UserService role-permission tests and audit mocks. They do not demonstrate all ten role workflows or a PostgreSQL migration/backup restore. Root is running the baseline suite and will record actual counts separately. No module is marked COMPLETE.
